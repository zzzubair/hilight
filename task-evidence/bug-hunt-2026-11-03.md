# Lavish bug hunt, 3 November 2026

Seven bugs reproduced in desktop Chrome on ser5ver. Fix the blocked sends, ambiguous annotation targets, and lost drafts before replacing upstream for Zubair's question-and-answer workflow. No application source was changed, and no PR was opened. The known Revisions Reveal highlight timing bug was excluded.

## Scope and evidence

- Fork: `zzzubair/lavish-axi`, assigned branch `boss/lavish-bug-hunt-report-only`, tested source commit `69bf3090b24a04773ffd05d2e0b23d91ca41923b`, version `0.1.96`.
- Host: ser5ver. Headless desktop Chrome `156.0.8078.79`, `/opt/google/chrome/chrome`, viewport `1440 × 1000`. The visible artifact frame is 1080px wide beside the conversation panel.
- Built the fork with the locked dependencies. Started its real `serve()` implementation on port `0`, which allocated an ephemeral loopback port. Set `LAVISH_AXI_STATE_DIR` to a new directory under `/tmp`, disabled telemetry and browser auto-open, and used the built `dist/cli.mjs` for poll and agent reply. Neither the live state directory nor port 4387 was used for this review.
- The fixture has twelve long sections, repeated nested targets, a text-selection target, question controls, a disclosure, a real clipping failure, and a revision registry added on regeneration. It needs no external assets.
- Interactions use Playwright's real clicks, typing, and browser navigation. Text selection uses a browser DOM Range followed by the SDK's mouseup event. The long transcript is seeded through the same agent-reply HTTP endpoint the CLI uses.
- Every confirmed finding was observed interactively, then reproduced by the saved [runner](bug-hunt-2026-11-03.mjs). Its [JSON output](bug-hunt-2026-11-03.json) includes CLI responses, browser state, and HTTP conflicts. Screenshots below show the real review page. The replay passed all its observation assertions and recorded no page JavaScript errors.

## Confirmed in browser

Ordered by damage to the question-and-answer loop.

### 1. A stale layout note prevents every unrelated question in the batch from being sent

**Severity:** blocks him. **Fix size:** M. **Upstream:** [#313](https://github.com/kunchenguid/lavish-axi/issues/313), partly fixed in this fork.

Reproduce:

1. Open Layout issues on the clipped-text fixture, select its issue, and click Queue selected fixes.
2. Regenerate the artifact with the clipping repaired. Wait for the issue to become Resolved.
3. Type an ordinary question in Conversation and click Send to Agent.
4. Follow the displayed advice to review the issues and click Send again. Poll still returns `waiting`.
5. Remove the stale layout note from the queue and send again. The same ordinary question is delivered immediately.

Observed: both sends return HTTP 409 and preserve both queued notes. Unlike the original upstream report, this fork does show an error. However, it tells the reviewer to retry without explaining that the resolved, unselectable issue's old queued note must be removed. An agent editing while the user asks another question can therefore block the entire exchange.

At fault: [SessionStore.#queuePromptsLocked](../src/session-store.js), lines 268–295, rejects the whole batch when `planLayoutWarningPrompt()` finds any conflict. [submitQueuedOnce](../src/chrome-client.js), around line 2241, provides retry guidance without retiring or identifying the stale queued entry. Consider retiring obsolete layout requests while preserving unrelated feedback; any acceptance change needs to preserve prompt identity and terminal-send guarantees.

Evidence: JSON entry `stale-warning-blocks-whole-batch`; [drawer before repair](06-layout-issues.png); [failed send after repair](07-stale-warning-send.png).

### 2. Clicking a second repeated block edits the first block's queued annotation

**Severity:** blocks him. **Fix size:** S. **Upstream:** [#445](https://github.com/kunchenguid/lavish-axi/issues/445), still present.

Reproduce:

1. Give two sections the same structure, with at least five nested `div` elements beneath their distinguishing section IDs.
2. Click the innermost block in section 1, type a question, and Queue it.
3. Click the corresponding block in section 2.

Observed: no annotation card opens for section 2. Conversation opens section 1's existing question for editing. The queued selector is `div > div > div > div > div`, matching all twelve repeated targets. The delivered poll carries that ambiguous selector too. This can prevent a question about the second block and send an agent toward the wrong block.

At fault: [createArtifactSdk.selector](../src/artifact-sdk.js), lines 799–823, stops after five ancestors even when the selector is nonunique. The click handler around line 2658 treats a matching selector as the identity of an already queued anchor. Extend the selector until it uniquely identifies the target, rather than merely increasing the depth cap.

Evidence: JSON entry `selector-collision`; [section 2 clicked while section 1's question is edited](01-selector-collision.png).

### 3. An agent save silently deletes an unfinished text-selection annotation

**Severity:** annoying, with irreversible draft loss. **Fix size:** M.

Reproduce:

1. Select words in the introduction and type a question in the Annotate text card. Do not Queue it.
2. Wait beyond the 120ms draft reporting debounce.
3. Have the agent save the HTML file, preserving the selected paragraph unchanged.

Observed: the new artifact loads with no annotation card. The question is absent from the queue, Conversation, and session storage. The source text still exists. The same experiment with an element annotation restores its draft correctly, so this is specific to text-range cards.

At fault: [createArtifactSdk.collectReviewState](../src/artifact-sdk.js), around lines 2141–2153, explicitly serializes `card: null` for `activeCardContext.tag === "text"`. [setReviewState](../src/chrome-client.js), around line 1192, therefore never receives the text to preserve. Avoiding an unsafe range restore is reasonable, but the words should survive as an Unsent annotation even when the selection cannot be restored.

Evidence: JSON entry `text-draft-lost-on-save`; [before agent save](04-text-draft-before-save.png); [after save, with the draft missing](05-text-draft-after-save.png).

### 4. Reloading the review page silently deletes an unsent Conversation message

**Severity:** annoying, with irreversible draft loss. **Fix size:** S.

Reproduce:

1. Type a question in Conversation without sending it.
2. Reload the same browser tab.

Observed: the composer is empty, the queue is empty, and no recovered draft is shown. Queued notes do survive the same-tab reload, making this behavior inconsistent. Take over here also reloads its own tab, so the missing composer persistence affects that path as well.

At fault: [chatInput input handler](../src/chrome-client.js), around line 4665, only hides a hint; no composer value is saved or restored. Existing persistence covers queued prompts and iframe review state, not `chatInput.value`. Save the composer draft on input and retire it only after it has been transferred safely into the durable queue.

Evidence: JSON entry `composer-lost-on-reload`; [question before reload](02-composer-before-reload.png); [empty composer after reload](03-composer-after-reload.png).

### 5. Incoming replies drag a long conversation away from the answer being read

**Severity:** annoying. **Fix size:** S.

Reproduce:

1. Build a long conversation with several multi-paragraph agent replies.
2. Scroll Conversation to the first answer.
3. Deliver another agent reply while the user reads it.

Observed: Conversation jumps from `scrollTop: 0` to `7116`, near the newest answer. This happens without a user send or any request to move. Repeated replies or receipt updates can interrupt comparison with earlier explanations.

At fault: [syncChat](../src/chrome-client.js), lines 1114–1139, rebuilds the transcript and always calls `scrollElementIntoView()` for the latest bubble. `render()` also unconditionally calls `scrollPanelToBottom()` around line 711. Preserve the reader's position when they have scrolled up and offer a new-message indicator; auto-follow only when already at the bottom.

Evidence: JSON entry `chat-scroll-jump`; [reading an older answer](08-transcript-reading-old-answer.png); [forced to the newest reply](09-transcript-forced-to-bottom.png).

### 6. A save resets expanded disclosures even while preserving the scroll position

**Severity:** annoying. **Fix size:** M. **Upstream:** [#469](https://github.com/kunchenguid/lavish-axi/issues/469), partly present.

Reproduce:

1. Expand the Supporting detail `<details id="details">` element.
2. Fill a `data-lavish-question` answer and scroll down to section 8.
3. Leave an element annotation draft open and regenerate the same file.

Observed: the disclosure changes from `open: true` to `false`. In the same run, scroll stays at 4439px, the question answer survives, and the element annotation draft reopens. Only the disclosure state is proven lost here; custom active-tab state was not tested.

At fault: [collectReviewState / restoreReviewState](../src/artifact-sdk.js), around lines 2110–2200, collect question controls and an element card but no disclosure state. The chrome then replaces the entire iframe document. Consider opt-in or stable-ID disclosure restoration without replaying synthetic input/change events.

Evidence: JSON entry `live-reload-state`; [restored element draft and long-page position](10-element-draft-restored.png).

### 7. Artifact saves grow tab history until Chrome refuses script-based closing

**Severity:** annoying. **Fix size:** M. **Upstream:** [#426](https://github.com/kunchenguid/lavish-axi/issues/426), still present.

Reproduce:

1. Open the review in a fresh browser tab.
2. Save the artifact several times, letting each live reload finish.
3. Read `history.length`, then call `window.close()` from page automation.

Observed: one measured save grows history from 4 to 5. At length 5, `window.close()` leaves the tab open and Chrome warns, `Scripts may close only the windows that were opened by them.` This matters to an agent cleaning up completed review tabs. Closing with the browser's tab control still works.

At fault: [replaceArtifactFrame](../src/chrome-client.js), especially line 3608, assigns `frame.src` on reload, adding joint session-history entries. The no-gate path around line 3487 also assigns `src`. Any replacement-navigation repair must respect the artifact's opaque-origin sandbox and retain load-token, retry, and revision-legend behavior; the suggested upstream code should not be copied without that verification.

Evidence: JSON entries `live-reload-state` and `history-prevents-script-close`, including Chrome's warning.

## Suspected from code

These are separate from the seven browser reproductions. No incorrect agent edit, cross-task delivery, or receiver crash was induced.

### A. Pure questions still produce an instruction to edit the artifact

**Symptom:** the poll guidance tells an agent to apply changes even when the reviewer explicitly asked for answers first. **Severity:** annoying. **Fix size:** S.

Reproduce: send the fixture's four questions, including `Please answer the questions before changing anything.`, then inspect poll's `next_step`. The captured output starts `Apply the requested changes to ...` and `Do not respond to the user just yet.`

At fault: [createFeedbackNextStep](../src/cli.js), around lines 660–663, uses a modification-first prefix for every ordinary feedback batch. The wording itself is verified in the CLI evidence. Its effect on a particular agent is an inference, since an agent may correctly prioritize the user's words. Neutral guidance should tell the agent to respond to the actual feedback through Lavish, changing the artifact only when requested.

### B. Session ownership is still a poll-listener claim, not the task that opened the review

**Symptom:** a different task can consume the next question once the original listener exits. **Severity:** blocks him when multiple agents share state. **Fix size:** L. **Upstream:** [#350](https://github.com/kunchenguid/lavish-axi/issues/350), partly addressed.

Reproduce to verify: have task A open a file and stop polling, then have task B poll the same file before sending feedback. Check whether B receives A's questions without an opening-task ownership transfer.

At fault: [the poll handler in serve](../src/server.js), starting around line 879, claims `activePolls` by session key. It now rejects a second concurrent listener and supports explicit poll takeover, fixing the upstream race between simultaneous pollers. It does not bind the session to the creating task across listener lifetimes. An owner label is not durable task authorization. Cross-provider resumption was not tested here.

### C. A successful HTTP delivery still lacks an explicit consumer acknowledgement

**Symptom:** a receiver dying after the response is written can leave feedback consumed before the agent has retained it. **Severity:** blocks him if that failure occurs. **Fix size:** L. **Upstream:** [#296](https://github.com/kunchenguid/lavish-axi/issues/296), partly addressed.

Reproduce to verify: let the poll response complete at the transport layer, discard its body or terminate the receiving harness before it records the result, then poll again. Check whether the identical batch is available with a stable receipt.

At fault: [SessionStore.takeFeedback](../src/session-store.js), around lines 620–684, drains the queue; [the poll completion path](../src/server.js) considers successful response delivery final. The fork has real improvements: disconnected writes restore feedback, per-note Seen/Working/Done receipts exist, and no-listener presence is visible. Those are different from a leased batch plus explicit consumer ACK. Do not infer that ordinary disconnect recovery is broken from this remaining protocol gap.

## What worked

- Element annotation, selected-text annotation, three queued notes plus a freeform question, Send to Agent, built CLI poll, and `poll --agent-reply` all completed through the real browser/server path. Poll delivered four distinct prompts with the selected text's range boundaries.
- Regenerating the HTML added a valid registry. Revisions showed one revision and one marked block. Reveal scrolled to section 9, putting the changed block at 457px in the frame. The known highlight timing defect was deliberately not assessed or reported.
- The layout drawer detected the real clipping, allowed selecting and queuing it, and resolved it after repair. Passive detection did not appear in the four-note poll as an unsolicited layout task.
- Supported element drafts, question-control answers, and long-page scroll position survived a save. Queued notes survived a full same-tab reload.
- Two tabs each kept their own queue. After a new tab took the review and a save exposed the superseded state, Take over here restored the source tab's own queued question. The other tab's Reload artifact then showed its takeover warning. No claim was made that drafts synchronize between tabs. [Superseded source tab](11-source-tab-superseded.png), [source tab after takeover](12-source-takeover-restores-own-queue.png).

## Repository checks

The build and saved Chrome reproduction passed. `pnpm run check` passed build, lint, formatting, and typechecking, then exited nonzero with **1,551 tests passed, 18 failed, and 8 skipped**. The [complete host-run log](bug-hunt-2026-11-03-check.txt) records the results.

- Fourteen tests in `test/input-copy-all.browser.test.js` and three in `test/whiteboard-render.browser.test.js` failed with `Chrome did not dump the fixture DOM in time`. Their cause was not established in this hunt. These are not evidence that the seven reported review-flow bugs caused the failures; the separate Playwright review-flow reproduction passed.
- One server-discovery test failed with `EADDRINUSE` while allocating a temporary loopback port. A focused rerun passed: [retry log](bug-hunt-2026-11-03-discovery-retry.txt). The suite's failure is retained above rather than replaced with a green result.
- Skill and plugin freshness checks passed when run explicitly, since the failed test command prevented the combined check from reaching them. Final evidence formatting, JavaScript syntax, and `git diff --check` passed.

The first sandboxed check attempt could not run server tests normally; the results above are from the subsequent host-access run. No test or application source was changed to make a check pass. The isolated review server and Chrome processes were closed at the end of each browser run.
