<h1 align="center">Hilight</h1>

<h3 align="center">Review the HTML pages your agent makes, right in the browser.</h3>

Your coding agent writes a plan, a comparison, or a diagram as an HTML page. Hilight opens that page in your browser. You click a heading, a table row, or a sentence, leave a comment, and press Send. The agent gets your comments, edits the same page, and the page reloads in place.

- **Local-first** - Pages are served from your machine by a small local server. Nothing leaves your computer unless you choose `hilight share`.
- **Comments on the exact spot** - Annotate elements and selected text, reply in comment threads, and edit Mermaid diagrams as whiteboards.
- **Built for agents** - Hilight is an [AXI](https://axi.md): a CLI any capable agent can run, with compact output and long polling, so it costs few tokens.

Hilight is a fork of [Lavish](https://github.com/kunchenguid/lavish-axi) by Kun Chen, renamed and maintained by Zubair Shaik. All the core review features come from Lavish.

## Install

Paste this to your agent and it installs Hilight for you:

```text
Install Hilight for me: run `npm install -g https://github.com/zzzubair/hilight/releases/latest/download/hilight-axi.tgz`, then `npx skills add zzzubair/hilight --skill hilight -g -y`. Check it worked with `hilight --version` and confirm the hilight skill is in ~/.agents/skills (and ~/.claude/skills if Claude Code is installed). If npm or Node is missing, tell me what to install instead of guessing.
```

### Or install by hand

You need Node.js 22 or newer.

```sh
npm install -g https://github.com/zzzubair/hilight/releases/latest/download/hilight-axi.tgz
npx skills add zzzubair/hilight --skill hilight -g -y
```

The first line installs the `hilight` command. The second installs the `hilight` agent skill for every project ([`npx skills`](https://github.com/vercel-labs/skills) writes it to `~/.agents/skills/hilight` and links it into `~/.claude/skills/` when Claude Code is installed). Drop `-g` to install the skill for the current project only.

Run `hilight update` later to reinstall from the newest release.

### From source

Use this if you want to change Hilight itself.

```sh
git clone https://github.com/zzzubair/hilight.git
cd hilight
pnpm install --frozen-lockfile
pnpm run build
npm link
```

`npm link` puts your checkout's `hilight` command on your PATH.

### Moving from Lavish

Hilight keeps using `~/.lavish-axi` when that folder exists and `~/.hilight` does not, so open review sessions carry over. Every `HILIGHT_*` environment variable below also accepts its old `LAVISH_AXI_*` name. If you had `lavish-axi setup hooks` installed, run `hilight setup hooks --replace-lavish` to swap the old hooks for Hilight ones.

## How agents use it

Once the skill is installed, ask for anything that is easier to read as a page (a plan, a comparison, a diagram, a report). In Claude Code you can also call it directly:

```
/hilight let's discuss our plan here
```

The agent then runs this loop:

1. Write the page, for example `.hilight/plan.html`.
2. Run `hilight .hilight/plan.html`. Your browser opens the page.
3. Run `hilight poll .hilight/plan.html`. This waits until you press Send.
4. Read your comments, edit the same file, write the answer to a reply file, and run `hilight poll <file> --agent-reply-file <reply-file>`, which posts the reply and waits again. A line `## c1` in the reply answers comment thread c1.
5. Stop when you end the session from the browser.

Every step is a plain command with output on stdout and an exit code, so any agent with a shell can run the loop, in bash, zsh, fish, PowerShell, or cmd. Hooks, the skill, and the plugin are optional. Replies go through a file, so no shell has to quote a multi-line body.

- **Only what is new** - Each poll returns one compact row per comment (`thread_id`, `on`, `text`, and `files` when it has images or a whiteboard), never the earlier back-and-forth of a thread, and a `changes` line for code cards that moved since the agent's last turn and for new canvas marks. `--full` adds the page snapshot and every prompt field.
- **Comments sent while the agent works** - If you send more comments after a poll handed the agent a batch, its next reply is held instead of posted (`status: held`) and those comments come back with it, so one reply answers everything and nothing waits for another turn.
- **Catching up** - Hilight never guesses whether an agent remembers the review. Every poll ends with one line pointing at `hilight catch-up <file>`, which summarizes the board, open threads with their last message and who is waiting, the resolved count, comments not yet delivered, and changed code cards; `hilight catch-up <file> c2` prints one whole thread.
- **When something goes wrong** - A server restart (an update, a crash, a supervisor) no longer kills the agent's poll: it reconnects for up to 30 seconds and keeps waiting, and queued comments are kept. `hilight status <file>` says what is going on right now (the server's pid, uptime, last restart and why, whether an agent is listening or since when and why not, comments waiting, and the last delivery, held reply and posted reply with times). `hilight log <file> --since 30m` prints the session's history. Every server error names the cause (`why`) and carries the last few relevant lines of `server.log` (`log`), so the agent can explain it without digging.

The skill itself is a short stub. It points the agent at `hilight --help`, which lists every command, so the instructions always match the installed version. If `hilight` is not installed, the skill tells the agent to run the same commands through `npx -y https://github.com/zzzubair/hilight/releases/latest/download/hilight-axi.tgz`.

## Other ways to use Hilight

### Session hook

Want Hilight's context, including your open sessions, at the start of every agent session instead of loading on demand?

```sh
hilight setup hooks
```

This installs a `SessionStart` hook for **Claude Code**, **Codex**, **OpenCode**, and **GitHub Copilot CLI**. Unlike the skill, the hook also lists your live sessions, so a fresh agent session can resume a review. Restart your agent session afterwards.

### Agent Plugin

Hilight also ships as an [Agent Plugin](https://agent-plugins.org). The installed package is the plugin: `plugin.json` sits at the package root next to `skills/`. Register it with every supported client it finds (**VS Code**, **Cursor**, **GitHub Copilot CLI**):

```sh
hilight setup plugin
```

It is opt-in and idempotent, and it repairs the registered path after a reinstall. A client that cannot be registered is reported and never blocks the others.

To register by hand, point a client at the package directory (`$(npm root -g)/hilight-axi`):

| Client             | Register with                                                                                                     |
| ------------------ | ----------------------------------------------------------------------------------------------------------------- |
| VS Code            | `"chat.pluginLocations": { "<package-dir>": true }` in user settings                                              |
| Cursor             | link the package dir at `~/.cursor/plugins/local/hilight-axi` (`setup plugin` handles Windows link compatibility) |
| GitHub Copilot CLI | `copilot plugin install <package-dir>`                                                                            |

Codex installs plugins only from marketplaces, so Codex users should use the session hook. Hilight declares no MCP server: the CLI is the agent interface, and the plugin brings the same `hilight` skill.

## How It Works

```
┌───────────────┐
│ Agent writes  │
│ artifact.html │
└───────┬───────┘
        ▼
┌────────────────────────┐
│ hilight <file_path> │
│ opens local browser UI │
└───────┬────────────────┘
        ▼
┌────────────────────────┐
│ Human annotates text   │
│ or elements, sends     │
│ chat, or queues layout │
│ issues from the inbox  │
└───────┬────────────────┘
        ▼
┌────────────────────────┐
│ hilight poll waits  │
│ and returns prompts    │
│ the user queued        │
└────────────────────────┘
```

- **File-path identity** - Sessions are keyed by the canonical HTML file path, so agents do not need opaque IDs.
- **Portable artifacts** - The artifact runs in a sandboxed iframe while Hilight injects a small SDK for annotations, snapshots, feedback controls, and render-time layout checks.
  Author-defined links and popups can open in top-level tabs, while artifact documents remain sandboxed without same-origin access.
  Hilight does not inject any design system, so the saved HTML file renders identically whether you open it through `hilight` or directly in a browser.
  Run `hilight design` for the single source of agent-facing design guidance, including optional CDN snippets and the whiteboard (Mermaid) opt-in snippet.
- **Self-paint warning** - `hilight <html-file>`, `export`, and `share` run a render-free check for artifacts missing an explicit page background and return a one-line `self_paint_warning`.
  The check fails open - any stylesheet link, `@import`, Tailwind runtime script, `color-scheme`, or `html`/`body`/`:root` background signal suppresses it - and it never blocks the open.
- **Open-time layout gate** - The browser chrome masks an artifact only while the real in-iframe audit waits for fonts and final geometry.
  The first completed client-side check reveals the artifact, whatever it found and even if reporting that check to the server fails; the gate never holds the review hostage waiting for a repair or a network round-trip.
  The user can click **Show anyway**, and a bounded safety timeout fails open from every gate state. A normal load is never masked for more than 1.5 s, and the "Checking layout" card itself appears only if the wait outlasts that.
  If the review cannot load at all - the chrome's own script never runs, or the server does not answer the artifact's load request after several retries - the mask names the problem and offers **Check and reload** without removing the independent **Show anyway** escape.
  A review already loaded in another browser tab is named the same way, with a **Take over here** button that loads the artifact in the current tab, because Hilight loads an artifact in one tab at a time. The takeover warning reads "Unsent answers stay in the tab or window where you entered them; taking over in another window does not bring them along."
- **Layout issues inbox** - Detection is passive. After fonts and finite animations settle, the injected SDK confirms severe failures from direct rendered evidence such as materially escaped meaningful content or required controls, clipped text fragments, viewport reachability, or near-total semantic occlusion.
  Explicit ellipsis and line clamp, standard visually hidden accessibility text, intentional scrollers or masks, parent overhang, generic element scroll geometry, decorative overlap, and uncertain motion do not produce findings by themselves.
  Proven failures are filed in a **Layout issues** button in the top bar, which is hidden while nothing is unresolved and otherwise shows the unresolved count.
  Its drawer lists each issue with severity, a plain-language explanation, the affected viewport, the target/component identity, when it was last seen, and its lifecycle state, plus per-issue **Reveal** (highlight it in the artifact) and **Dismiss** actions.
  Nothing is selected by default. The user picks issues (or **Select all**) and **Queue selected fixes** turns that whole group into one ordinary queued prompt, tagged `layout-warnings`, that reaches the agent through the normal feedback path when they send.
  A queued fix request never blocks the rest of a send. If the agent already fixed (or the user dismissed) every issue it names before it is sent, it is dropped with a note saying so. If an issue it names changed after it was queued, it stays queued for the user to remove or re-queue while everything else is delivered; only a send made of nothing but such requests, or a **Send all and end session**, is refused.
  Detection never returns `hilight poll` and never wakes an agent; only the user queueing a fix does. The one exception is a fatal `artifact_failures` response, for failures that make the review itself unusable, such as the artifact document or one of its own local assets failing to load.
- **Layout issue lifecycle** - Each issue is identified by a stable fingerprint of the diagnostic rule, the normalized target identity, and the viewport class, so repeat detections update one record instead of inflating the count.
  `Open` means the latest completed check for its viewport still detects it. `Queued for fix` means the user asked for a repair - it stays unresolved and counted, and cannot be queued again while that request is outstanding.
  `Resolved` requires a newer successful artifact load plus a complete check at the same viewport that no longer detects it; it then leaves the count but keeps a bounded history.
  `Still present` (recurring) means a queued issue survived a newer revision, so it is selectable again with its earlier attempt retained. `Unverified` means a reload or check failed or was incomplete, so the prior issue was preserved rather than cleared. `Returned` means a resolved issue came back on a later revision.
  Dismissal applies only to the current artifact revision; a later revision surfaces the issue again if it is still detected. A check at one viewport never clears an issue found at another, and a viewport removed from the configured diagnostic set (`HILIGHT_DIAGNOSTIC_VIEWPORTS`, default all) is marked obsolete with an explicit reason rather than reading as fixed.
- **Revision marks** - Opt-in. After a round of feedback the agent regenerates the whole file, and a one-sentence edit is invisible on a long artifact. The agent can declare what it changed in the artifact itself: one `<script type="application/json" data-lavish-revisions>` array of `{ id, label, timestamp, summary }` entries, plus `data-lavish-revision="<id>"` on each block it edited or added. Run `hilight design` for the snippet.
  The top bar shows no revisions control. Instead, an agent reply in a comment thread that names a revision (`## c1 reveal=r2`) carries a **Reveal change** button that steps through that revision's marked blocks, flashing them one at a time. Artifacts with no registry are unaffected, a malformed registry is ignored rather than surfaced as an error, and at most 6 revisions are kept.
  Hilight never marks up the artifact for this, so the served page stays identical to the saved file, and the registry and marks travel with the file through export.
- **Live tab title and icon** - Opt-in. The browser tab adopts the artifact's `<title>` and first `<link rel="icon">` when it loads. A long-lived artifact can keep the tab current afterwards with `window.lavish.setDocumentMeta({ title, icon })`: a string sets the field (a title that is blank after trimming restores the load-time title), `null` restores the load-time value, and an omitted field is left alone. The title is trimmed to 120 characters and shown as `<title> · Hilight`; the icon must be a `data:image/svg+xml` URL of at most 8192 characters. Anything else is ignored. A value stays until the next call or until the tab itself reloads, so call again after each page update. The call is a no-op when the page is not open in Hilight, so feature-detect with `window.lavish?.setDocumentMeta?.(...)`.
- **Local assets** - Copy local images, CSS, fonts, and scripts next to the HTML artifact and reference them with relative paths from that directory; root-prefixed paths such as `/assets/logo.png` will not resolve through Hilight's artifact route.
- **Export and sharing** - `hilight export` writes `<name>.export.html` by inlining local assets only, stripping the annotation SDK, and leaving remote CDN/font references as links that still need network access.
  `hilight share` publishes the same local-inlined HTML to [ht-ml.app](https://ht-ml.app), a third-party hosting service not part of Hilight.
  Publishing sends the artifact to ht-ml.app's servers, public by default, or private and password-protected with `--private` (Hilight generates the password and returns it once, in the command output and in the browser publish dialog) or `--password <pw>` (one you supply, never echoed back). A generated password is a shared secret: give it to whoever should read the page, and expect it to appear in your agent's transcript, because the agent has to relay it. Hilight does not store it.
  The response includes a secret `update_key` shown once. Keep it to republish the same URL later with `--site <site_id> --update-key <key>`, which replaces the HTML in place and leaves the password alone unless you pass `--private` (rotate to a new generated one) or `--password <pw>` (set one). Locking a page that was public is not instant - it can keep answering from ht-ml.app's CDN cache for minutes after the password is set - while a page that was already private has no such cached copy.
  A page's password cannot be removed: ht-ml.app accepts a request to clear one and silently ignores it, so Hilight offers no way to make a private page public rather than telling you it did something the host did not do. Republish as a new page if you need a public URL.
  ht-ml.app has no delete endpoint, so `--unpublish --site <site_id> --update-key <key>` replaces the page with a short placeholder and locks it behind a discarded random password rather than removing it: the URL still resolves and the host still holds what was published. The content swap is immediate, but the lock is not: a page that was public can keep serving the placeholder to uncredentialed visitors from ht-ml.app's CDN cache for minutes afterwards. The `update_key` plus `--private` republishes real content behind a new password you can share.
  Bundling never fetches remote URLs, Hilight itself does not set a CSP, local reads stay confined and size-capped, and absolute `file://` paths outside safe inlined asset references are redacted before output.
  Per-asset and per-bundle inline caps default to 10 MB and 25 MB, overridable with `HILIGHT_EXPORT_MAX_ASSET_BYTES` and `HILIGHT_EXPORT_MAX_BUNDLE_BYTES`.
  Unresolved local assets or export notices such as author-set CSP meta tags and redacted file URLs are surfaced in command or browser output.
  Use `--token` or `HILIGHT_HTML_APP_TOKEN` for an optional bearer token when publishing a new page (a republish or `--unpublish` authorizes with the `update_key` instead and rejects `--token`); set `HILIGHT_HTML_APP_API_URL` to override the ht-ml.app API base and point `share` at a backend you control (see [Self-hosting the share backend](docs/self-hosting-share.md) for the contract it must implement).
- **Live reload** - Hilight watches the HTML artifact file by default and preserves review context across reloads: the artifact iframe scroll position, an open annotation card's unsent text (a selected-text card reopens on the same words when they are still there, and otherwise on the element that held them), disclosures (`<details>`) the reviewer opened or closed, and answers to `data-lavish-question` controls (application-owned form state is left alone). Reloads replace the frame's history entry, so saves do not grow the tab's back history. Supported review state and the unsent queue are saved in that tab's `sessionStorage` and survive a full reload of the review page in the same tab when browser storage is available. They are not shared with another tab or window; closing the owning tab can lose work that has not been sent. While a queued layout-issue batch is outstanding, closely spaced saves coalesce so one batch of fixes costs one refresh. To also reload on sibling asset changes, add `data-lavish-live-reload-root` to the root element or `<meta name="lavish-live-reload" content="root">`.
  If the element an unsent annotation was attached to is gone from the artifact for good, Hilight cannot reopen that card, and if the artifact replaces a queued note while you are editing it, the replacement is kept as the artifact sent it. Either way, Hilight writes your edited text into the page comment under **Unsent annotation** - selectable, never written over anything you have typed, and kept there across reloads; no note is ever dropped to make room for a newer one, and a note the browser refuses to store says so where it is shown.
- **Feedback controls** - Native controls (radios, checkboxes, inputs, selects, buttons, labels, disclosure summaries, contenteditable) and custom widgets with an interactive ARIA role (`button`, `checkbox`, `combobox`, `menuitem`, `menuitemcheckbox`, `menuitemradio`, `option`, `radio`, `switch`, `tab`, `treeitem`) are interactive automatically, so they do not need `data-lavish-action`. A link (`<a href>`) stays annotatable when it carries one of these roles or sits inside such a widget.
  Artifacts can start in explore mode with `data-lavish-annotate="off"` on the root `<html>` element so stray clicks do not open annotation cards. Annotation stays on by default (or with `"on"`); unknown values default to on. The toolbar reflects the page default and can override it; the reviewer's choice persists across artifact reloads within that review page. See `hilight playbook input` for author guidance.
  For reversible choices, let option clicks update local state, then queue exactly one final answer from a per-question submit or Queue answer button with `window.lavish.queuePrompt()`.
  If someone may open a decision artifact as a standalone HTML file, `hilight playbook input` provides an optional Copy all answers control they can use to paste their form answers back into chat.
  Mark only custom (non-native) clickable elements with `data-lavish-action` so Hilight does not annotate them, and use `data-lavish-question` or `queueKey` when pre-send updates for the same question should replace each other.
  Everything is a comment: a note on an element, a text selection, a table cell, a diagram node, a whiteboard, a layout-issue batch, or a message about the page as a whole. There is no separate conversation panel. Anchored notes become cards in the comments margin beside the artifact (see Margin comment threads), and anything not tied to one place - a general message, a whiteboard edit, a layout-issue batch - lands in the **Whole page** thread pinned at the top of that margin, with an anchor line naming what it was attached to and, when available, the selector on hover.
  New comments and replies are drafts first. Enter saves a draft, Shift+Enter adds a line, and Esc closes the box and keeps what you typed. A draft reads **Not sent** in its card's header, with **Edit** and **Delete** text buttons; clicking an anchored draft scrolls the artifact to the element it points at, and clicking that element again in annotate mode opens the same card rather than a fresh one. Saving a draft with no words and no images deletes it. One **Send to agent (N)** button, pinned at the bottom of the margin, delivers every draft in this tab in one poll round. While its batch is in flight a draft reads **Sending** and can no longer be edited, and once the server accepts it, it settles in place in every tab of the session. Drafts, including half-typed text in the page and reply boxes, survive a reload of the review page and every artifact save. The page thread keeps the newest stored transcript up to 5 MiB; older messages drop from view, but an accepted note still settles and is not sent twice. New agent replies never move the margin's scroll position.
  Agent replies render a small Markdown subset - paragraphs, line breaks, headings as bold lead lines, bullet and numbered lists, fenced and inline code, bold, italic, and http(s) links - while tables, images, and raw HTML stay as the text the agent wrote; your own messages keep their line breaks and are never parsed.
  The top bar holds only the essentials: the file name, a small agent status (**Not listening**, **Listening**, **Working**, or **Ended**; when the server knows, Not listening says since when and why, for example **Not listening since 23:05 · server restarted**, with the full sentence in its tooltip), the layout-issues inbox when there is one, an **N resolved** control, the Annotate switch, and an overflow menu. That menu has **Activity** (the session's history: when the agent listened, what reached it, when it replied, and why it stopped listening, with times), attach images to a page comment, copy path, reload artifact, copy DOM snapshot, export standalone HTML, publish link, **Send all and end session**, and **End session**. When the review is open in another tab, a notice under the bar offers **Take over here**.
  **Send all and end session** submits every draft and user-ended attribution together. Once it starts, Hilight pauses new feedback, waits up to 5 seconds for feedback preparation already underway, keeps any open annotation draft intact until delivery succeeds, then holds that exact terminal batch. A completed reservation survives a page reload, including when its prompts were already delivered and only the pending end remains; incomplete preparation is not restored. If preparation times out, Hilight keeps the review open and its existing drafts editable with a visible error. A transient delivery failure permits only retrying the same terminal batch through **Send all and end session** until it succeeds. If a snapshot makes the request too large (HTTP 413), Hilight retries that exact batch once without the optional snapshot. An actionable attachment rejection (HTTP 400), recoverable layout-selection conflict (HTTP 409), or unrecoverable 413 instead cancels the terminal reservation without ending the session, keeps the drafts, and restores editing, deleting, **Send to agent**, **Send all and end session**, and **End session** so the reviewer can revise or remove stale feedback before submitting again.
  Unsent drafts belong to the tab where you wrote them, not to a server-shared draft. An empty **Send to agent** reports "Nothing to send yet." followed by: "Unsent comments stay in the tab or window where you wrote them; taking over in another window does not bring them along." Annotate mode alone does not save a draft; the annotation card's **Save** (or Enter) does, and Esc keeps typed words as a draft too. Only feedback accepted by **Send to agent** is stored on the server for delivery to the agent.
  Send waits up to 5 seconds for the artifact's DOM snapshot, then delivers without that optional context if the frame no longer answers; a late snapshot cannot submit the batch twice. A failed or still-unacknowledged POST keeps the drafts and shows persistent recovery guidance unless a transcript sync proves the server already accepted that feedback.
- **Margin comment threads** - On desktop, every element, text, table-cell or diagram-node note becomes a comment card in a margin beside the artifact, lined up with what it is on. Commented text is not highlighted at rest: it carries only a faint underline (text) or a thin margin tick (elements), and gets its full highlight while you hover or focus its card or its text, and while its card is open. Cards stack without overlapping; the open card sits exactly beside its anchor and the others move out of its way. When anchors are too close together for full cards, cards shrink to a one-line summary of their latest message, and the open card expands. Click a card, or in annotate mode click the commented element or text, to open its reply box with focus in it. With a card focused, j or the down arrow moves to the next thread and k or the up arrow to the previous one, Enter opens it, and Esc closes it. A long thread folds its middle replies while the card is closed.
  Each card's header carries one plain status word: **Not sent**, **Sent** (the server has it), **Seen** (a poll took it), **Working** (the artifact changed after that), or **Replied**. A failed send reads **Not delivered · Retry**.
  **Resolve** hides a thread from the margin and from the page, and a **Resolved · Undo** notice stays for about 6 seconds. Nothing is lost: the **N resolved** control in the top bar lists resolved threads with their anchor text, and choosing one shows it with **Reopen**, which puts it back in place with its full history. Replying in a resolved thread, or an agent answer to it, reopens it. Threads, resolution and reply drafts survive reloads, server restarts and artifact revisions; a thread whose anchor is gone is listed in the same drawer under **No longer on the page**.
  The annotation popup opens on one click (or a text selection) with focus in it. Enter (or **Save**) saves the comment as a draft, Shift+Enter adds a line, and Esc closes it and keeps typed words as a draft.
  Poll prompts on an anchored note carry a short `thread_id` (`c1`, `c2`, ...). The agent answers threads in one ordinary reply: a line `## c1` starts that thread's answer, and `## c1 reveal=r2` also gives it a **Reveal change** button that jumps to the blocks marked `data-lavish-revision="r2"` in the page's revisions registry. Text before the first such line goes to the **Whole page** thread. A reply without any such line answers what the agent was handed: when every note in it came from one thread (a single card comment, say) the reply goes into that thread, and otherwise it goes to **Whole page**. The `hilight reply` receipt's `threads` lists where it landed. An unknown thread id rejects the whole reply, so nothing lands in the wrong place. Each poll row carries the prompt's `thread_id` and an `on` column naming its card or text; a thread with new messages sends only those.
- **Reviewing on a phone** - Below 860px wide, the artifact takes the whole screen above a **Comments** dock, and the comments open as a bottom sheet over it, with the page thread first and every other thread stacked in page order: tap the dock, swipe it up, or press the chevron to raise it; tap the dimmed artifact, swipe the sheet down, press the chevron, or press Escape to lower it. The dock reports what matters while the sheet is down - how many drafts are not sent, a reply that arrived while you were reading, or whether the agent is listening - and the sheet stays open across a reload of the review page. The sheet sizes itself to the visible viewport and respects safe-area insets; if the keyboard or attachments leave little room, the threads scroll while **Send to agent** stays pinned above the bottom edge. In landscape the sheet covers the top bar as well. Wider screens keep the side-by-side margin. A small chevron handle on the margin's left edge folds it away so the artifact or board gets the full width; folded, it becomes a slim tab on the screen's right edge that shows how many drafts are waiting, and Hilight remembers the choice per session. Starting a thread unfolds it again.
- **Keyboard shortcuts** - In the page comment box, the annotation card, and every thread's reply box, Enter saves a draft, Shift+Enter inserts a newline, and Escape closes the box and keeps the draft. In the annotation card an image still uploading or failed keeps the card open. Only **Send to agent** sends.
  While editing a draft, Enter saves it, Shift+Enter inserts a newline, and Escape discards the edit.
  With a comment card focused, j / ArrowDown and k / ArrowUp move between threads in page order, Enter or Space opens the focused thread, and Escape closes it.
  Cmd+I or Ctrl+I toggles between annotate and explore mode from either the browser chrome or the artifact iframe, including while focus is in a textarea or control.
  In annotate mode a plain click on a link annotates it; Ctrl+click (Cmd+click on macOS) follows the link instead, opening it in a new tab as the browser normally would, without leaving annotate mode. Off macOS, Meta+click (the Windows or Super key) annotates like a plain click.
- **Agent presence** - The browser shows when no agent is listening and keeps human feedback actions available while the agent is working. Feedback accepted by **Send** is queued on the server for the next successful `hilight poll` delivery even across reloads; never-sent notes remain in the originating tab. An agent reply concludes delivered work and returns presence to waiting (see the CLI Reference for reply and poll commands). A supervisor-owned process listener is shown as an external listener rather than an idle captain turn.
- **Delivery status** - Every comment thread shows one muted status word, right-aligned in its header, that moves forward as the server observes the note: **Not sent** while it is a draft, **Sent** once the server has it, **Seen** when a `hilight poll` takes it, **Working** when the artifact file changes after that, and **Replied** when the agent answers. All of it comes from what the server observes; the agent does nothing extra. A note answered without touching the artifact goes from Seen to Replied. A reply marks every note the agent has seen as Replied, not notes still waiting for a poll. If a send fails, the drafts read **Not delivered · Retry**, and **Retry** is a text button that sends again. Beside the word is the time of that state; its tooltip has the whole trail (sent, delivered to the agent, agent working, answered). The top bar's agent status says whether an agent is listening at all.
  In a Herdr-managed pane, set `HILIGHT_HERDR_CHIME=1` to show a Herdr request notification and play its chime once an indefinite poll enters the waiting state. Immediate queued feedback and timed debug polls do not trigger a notification. The integration is off unless both `HILIGHT_HERDR_CHIME` and Herdr's `HERDR_ENV` session marker equal `1`; leaving either unset or using any other value opts out. Notification delivery runs without blocking feedback: if Herdr is unavailable, rejects the notification, stalls, or fails, the poll continues unchanged.
  Closing the last review tab while a poll is active starts a reconnect grace period, 10 seconds by default. A reload or quick reconnect keeps an active poll waiting; if every review stays disconnected, the poll returns `browser_disconnected` without ending the resumable session, and the agent asks whether to reopen or end it instead of acting uninvited.
  A phone that locks its screen or backgrounds the tab drops the connection too, so set `HILIGHT_DISCONNECT_GRACE_MS` on the server to a longer millisecond budget, or to `0` or `off` so a disconnect never ends the poll (it then waits for feedback, an end, or its own timeout). Empty or invalid values keep the 10-second default.
  The no-timeout poll always writes an immediate stderr banner so it is visibly not hung; it adds the periodic stderr wait ticks only in an interactive terminal, so when stderr is piped (as under agent harnesses) the captured output carries no tick noise. Stdout always stays reserved for the final response; if the poll is interrupted or times out before feedback arrives, re-run it because feedback remains queued until delivery. Poll delivery consumes the response, so read the complete response before truncating or filtering it.
  Codex-specific guidance keeps that poll attached to the active turn instead of hiding it in a background task, because completed background tasks may not resume the agent.
- **Session end etiquette** - Hilight tracks who ended a session: a human clicking **End session** (or **Send all and end session**) in the browser is a user-initiated end, while `hilight end <html-file>` is agent-initiated.
  When either side ends the session, every open review tab becomes visibly read-only and disables its feedback controls; feedback submitted after the end is refused instead of being accepted without an agent to receive it.
  A plain `hilight <html-file>` after a user-initiated end refuses to reopen the browser and returns guidance instead; pass `--reopen` only when the user asks for further review or something important needs their visual attention.
  Agent-initiated ends keep reopening normally, same as before.
  `hilight poll`'s `ended` response and the `feedback` response for the final batch before an end both carry `next_step` guidance telling the agent to stop polling and deliver remaining updates in chat instead of reopening.
- **Precise targets** - Text annotations include selected text plus range anchors, and text selections carry those anchors only.
  Clicking an element inside a table also carries the cell's visible row and column names alongside the exact CSS locator, so filtered or sorted rows do not make feedback look misdirected.
  When merged cells make either name ambiguous, Hilight leaves that name out rather than guessing; an explicit `<th scope="row">` remains authoritative even when a `rowspan` makes the row's position ambiguous.
  The CSS locator still points at the exact element you clicked, so an annotation with an omitted name is only less descriptive, never mislabelled.
- **Image attachments** - Attach reference images (PNG, JPEG, WebP) in either the page comment box or an annotation card by pasting, drag-dropping, or using its image picker; each image shows a thumbnail chip with upload, remove, retry, and error states. If a sent image is later evicted under the attachment storage limits, its transcript-history thumbnail becomes an **Image expired** placeholder.
  A paste containing both text and images preserves the text while attaching the images (a copied file's own name or path is treated as placeholder and not pasted). Page comments may contain text and images together or images only.
  Images are stored under the state dir and the queued prompt carries a server-generated absolute `path` and content-hash `id` (plus mime and dimensions) - never the raw bytes - so `hilight poll` hands the agent a local file path to open.
  Limits are `HILIGHT_MAX_ATTACHMENT_BYTES` (default 10 MiB per image), `HILIGHT_MAX_ATTACHMENTS_PER_PROMPT` (default 4), and `HILIGHT_MAX_PROMPT_ATTACHMENT_BYTES` (default 25 MiB per prompt); if any image is missing or any prompt breaches a count or byte cap, the entire send batch is rejected, the queue is preserved, and the reason is surfaced in the composer rather than silently dropping images.
  As a browser-side abuse guard, each chrome page allows 30 upload attempts per rolling minute, 4 uploads in flight at once, and 256 MiB of attempted image bytes over its lifetime; rejected uploads stay visible for retry or removal.
  Unreferenced attachments expire after `HILIGHT_ATTACHMENT_TTL_MS` (default 7 days; `0`/`off` disables); `HILIGHT_MAX_ATTACHMENT_DISK_MB` (default 512 MiB; `0`/`off` disables) caps total attachment disk and may evict older unreferenced images sooner.
  The cap is enforced when an image is uploaded, not just periodically: the upload first reclaims unreferenced files (oldest first, and never one added within the last hour), and if it still would not fit, that upload is refused with a storage-full error on its chip instead of discarding an image the user is about to send.
- **Mermaid diagrams** - Whiteboards are an opt-in: agents author a diagram as Mermaid only when you ask for an editable whiteboard, and hand-authored inline SVG illustrations are the default figure medium otherwise.
  In the Hilight browser, every rendered Mermaid diagram in a `.mermaid` container becomes an embedded editable Excalidraw whiteboard.
  Click a diagram to unlock editing, and use its Fullscreen action to edit it over the whole viewport.
  Whiteboard scenes autosave locally.
  If a live reload changes the Mermaid source, an unmodified whiteboard silently re-converts to the new diagram. If the reviewer had edited the scene, reopening it lets them re-convert and discard the saved edits or keep editing the saved scene.
  Use **Queue feedback** to add a bounded edit summary plus local `.excalidraw` scene and PNG preview paths to the page comment as a draft, then click **Send to agent** to deliver it.
  The agent updates the artifact's Mermaid source, which remains authoritative.
  Flowchart, sequence, class, ER, and state diagrams convert to editable shapes; other diagram types are images that reviewers can draw and annotate.
  Hilight changes only the browser view, so saved, standalone, and exported artifacts still render plain Mermaid.
- **Whiteboard libraries** - Copy Excalidraw library files (`.excalidrawlib`, for example from [libraries.excalidraw.com](https://libraries.excalidraw.com)) into `~/.hilight/excalidraw-libraries/`, or `HILIGHT_STATE_DIR/excalidraw-libraries/` when set. Every whiteboard's library panel lists their items, and an item you drop on the canvas reaches the agent by name in the edit summary.
  Agents run `hilight libraries` to find item refs and can show a flowchart node as one of those icons by adding a `%% lavish-icon <node-id> <library-id>/<item name>` comment to the Mermaid source. Mermaid ignores the comment, so saved, exported, and shared copies, and whiteboards missing that library, show the plain node.
  Hilight only reads that directory and never downloads libraries. Files over 10 MB, more than 25 MB or 5,000 items in total, and unreadable files are skipped; `hilight libraries` lists each skip with its reason.
  Each library carries its author's terms (AWS Architecture Icons, for example, are covered by AWS's own usage terms), so check them before using one.
- **Boards** - A board is one HTML file whose `<main data-hilight-board>` holds `<section>` cards and named flows. Opened directly it is a plain page of cards; in Hilight it becomes a pan-and-zoom canvas. The agent writes only what is on it; Hilight lays the cards out, routes the arrows, colours the flows and picks the zoom.
  A card is rich HTML, a code card pinned to a line range of a real file (`data-code="src/server.js:120-180"`), or a nested board you double-click to open one level deeper. A flow is an `<ol data-flow="Name">` whose items are steps such as `api:12-18 -> store:40-44 saves the order`: each step is an arrow that starts on those lines of the first card and ends on those lines of the second, with both ends highlighted. Arrows route around every card they do not join, each flow has its own colour named in a small legend card in the canvas corner, and each flow gets its own band of cards. Text written directly in `<main>` is the board's summary. `hilight board check` lists any card or step it cannot place, in words that say what to write instead.
  Code cards are read from disk when the board opens and re-read while it stays open, so the canvas shows the live code. A code card is as wide as its longest line, up to 100 columns, and longer lines wrap with a ↪ marker instead of being cut off. The board opens on its top row at a readable zoom, and in a small window (a half-screen laptop, a preview pane) on the first card of the first flow; **Fit** shows the whole level. A view you chose is kept for a window of about the same size; in a much smaller or larger window, or when you resize before moving the camera, the board picks its opening view again. A board keeps the desktop layout at every window size, and a window narrower than 1000px folds the comments margin, also after a resize, until you open or fold it yourself. On a phone, where touch is the only input, a board page shows "Canvas boards aren't supported on phones yet. Open this link on a laptop or desktop." instead of the canvas; the test is the input, never the width, so a small desktop window or a laptop with a touchscreen still gets the board. Other pages are unchanged. A card whose lines changed since `hilight board stamp` pinned them turns **Stale** and marks the changed lines; a card whose lines only moved follows them. Paths resolve inside the git repository that holds the board, and nothing outside it is read.
  A board page has one top bar: the board's title (its summary behind the info button), one status pill that merges code-card health with the resolved and off-page counts, the agent status, Annotate and the menu. Review comes first, so the drawing tools stay hidden until you press **Draw** (or pick a tool by its shortcut). Draw arrows, circles, boxes and notes over the cards, then press **Queue marks** in the comments panel, with an optional note beside it: the agent receives them in words ("Circled lines 678-682 of src/session-store.js in card #store"). Select a card and press **Comment** to start a margin thread on it. The canvas layout and your marks live in Hilight's state, never in the file, and survive reloads.
  Two-finger scroll pans and pinch zooms around the pointer, the same on macOS and Windows precision trackpads (ctrl or cmd + wheel zooms with a mouse); zoom steps are proportional, wheel-delta spikes are clamped, and a sideways swipe never turns into browser back or forward. Scrolling over a code card you have shrunk scrolls its code first, and its arrows follow. Draw, undo, redo, zoom and fit share one small dock in the canvas's bottom-left corner; Excalidraw's own menu and library are hidden on boards. Fit, and the opening view, redo themselves when the comments margin opens or folds; a view you chose keeps its centre.
  When the agent changes the board, cards and flow steps you have not seen yet are marked **New** (a ring and a pill on the card, a heavier arrow). A small toast on the canvas names them, the camera glides there after a moment, **Back to where I was** returns to your view, and **Got it** clears the marks. Until then they stay New across reloads. An agent reply that names a revision (`## c1 reveal=r2`) also carries **Reveal change**, which jumps to the card marked `data-lavish-revision="r2"`.
  Run `hilight playbook board` for the authoring rules. A demo of Hilight's own architecture is in `docs/examples/hilight-architecture.html`.
- **Server cleanup** - The detached server stops after the last session ends when nothing is connected, or after `HILIGHT_IDLE_TIMEOUT_MS` (default 30 minutes) with no browser or poll connections.
  Set `HILIGHT_IDLE_TIMEOUT_MS=0` or `off` to disable idle self-shutdown.
- **Poll reconnect** - A `hilight poll` whose server goes away reconnects for up to 30 seconds (`HILIGHT_POLL_RECONNECT_MS` shortens it, for tests and debugging). For the first 3 seconds it only waits, so a supervisor such as systemd can bring its own server back first; after that it starts one. A reply sent with the poll is never sent twice: once the server answered, a reconnect only listens again.
- **Server upgrades** - One background server serves every session, so upgrading `hilight` while reviews are open makes the next `hilight <html-file>` replace that server. Only a newer CLI replaces an older server: a CLI older than the running server uses it as is, so two installed versions on one machine do not restart each other's server. Releases up to and including 0.1.86 still replace a server of a different version, so this turn-by-turn restart stops only when both installed versions contain this fix. Only the review page for the artifact being opened reloads itself once the replacement answers - and not even that one while you have unsent annotation text open, which gets the same banner instead so the reload is yours to make. Every other open review page keeps working and shows a banner reading "Hilight was updated. This page is running the previous version.", with a Check and reload button and a Dismiss button, so no page you are reading reloads on its own. After `hilight stop` those pages say Hilight was stopped and to reload after you start it again, and a restart that only picks up a local build says that rather than claiming an update. An open review page whose server simply goes away - idle self-shutdown, a crash, a machine that slept - shows that same banner once reconnecting has failed for a few seconds, rather than retrying a dead server silently while looking fine; it clears itself if the server comes back, and dismissing it keeps it dismissed until then.
  A page still using the legacy event stream reloads once when it reconnects to the replacement server, moving itself onto the current transport without retaining an HTTP connection. If unsent annotation text is open, it shows the neutral server-restarted banner instead and waits for you to reload.
  Every **Check and reload** control asks the server whether it is running before it navigates; while nothing answers, the page stays where it is and says so, and a check that gets no answer at all says that instead of guessing.
  In-flight `hilight poll` commands end with an interrupted-poll error and are safe to re-run; server-accepted feedback remains queued until delivery, while never-sent notes and supported annotation drafts survive a same-tab reload as described under **Live reload**.
  A page waits for the replacement rather than reloading into a port nothing is listening on, and tells the user to restart Hilight if it never returns.
- **Local-first state** - Session state stays under `~/.hilight/` by default, or `HILIGHT_STATE_DIR` when set. A machine that already has `~/.lavish-axi/` and no `~/.hilight/` keeps using `~/.lavish-axi/`.
- **Diagnostic viewports** - `HILIGHT_DIAGNOSTIC_VIEWPORTS` sets which viewport classes the layout-issue inbox tracks (`mobile`, `compact`, `desktop`; comma-separated, default all). Warnings whose class leaves the set are marked obsolete with an explicit reason instead of silently reading as fixed.
- **Server port** - Set `HILIGHT_PORT` to choose the server port; it defaults to `4387`.
- **Network binding** - With Tailscale running, the review server automatically listens only on loopback (`127.0.0.1`) and this machine's Tailscale IPv4 address - never on `0.0.0.0` or every interface. The generated session link uses the machine's MagicDNS name, so it is the phone-ready URL to open from another device on the same tailnet. When Tailscale is absent or down, Hilight silently falls back to loopback-only and prints no phone URL. If Tailscale is running but MagicDNS is unavailable, Hilight visibly warns that phone access is unavailable and remains loopback-only. Binding beyond loopback exposes an unauthenticated server that can read and serve arbitrary local files to devices that can reach it, so the tailnet should be trusted. Any explicit `HILIGHT_HOST` overrides automatic Tailscale binding; wildcard values are restricted to loopback, while a non-wildcard value selects that concrete bind address, and the server listens on loopback as well so every local CLI finds it whatever its own `HILIGHT_HOST` says. An address that cannot be bound - the tailnet address while another process holds it, while Tailscale restarts, or an explicit hostname that temporarily does not resolve - is reported as `network_warning` in `hilight <file>` output and logged to `server.log`; session links point at loopback meanwhile unless `HILIGHT_LINK_HOST` overrides them, and the server keeps retrying that address in the background and immediately on the next CLI invocation. Once it binds, the warning clears and new session links use it again, with no restart. If no listener can bind, startup fails rather than claiming a reachable server. `HILIGHT_LINK_HOST` controls the link host when automatic Tailscale binding is disabled.
- **One server per port** - Agents on one machine can run with different `HILIGHT_HOST` settings, or none, and still share one server: before starting one, the CLI looks for a running server on its configured host, loopback, and every other local address. A running server that was never asked to listen on the address a CLI's `HILIGHT_HOST` names is replaced once by a server that listens on that address plus every address the old one served, keeping all sessions. Upgrade and network-change restarts keep every address the old server served in the same way, except an address that is no longer on this machine. Switching to an address the running server already serves, including loopback, reuses it, so run `hilight stop` first to drop an address. Another server of the same installation (the same state directory) found on the same port at a different address is shut down through its own shutdown endpoint, after the kept server is made to serve that address too, so review links already handed out there keep working. A server belonging to another state directory that reports its installation identity is never used, replaced, or stopped: when it holds loopback or the configured address, the CLI fails with an error naming its state directory, so pick another `HILIGHT_PORT`. Older servers that cannot report an identity are treated as belonging to this installation only at those control addresses, for upgrade compatibility.
- **Allowed hosts** - To defend against DNS rebinding, the server rejects (`403`) any request whose `Host` header is missing or not one it answers to: loopback names plus the concrete Tailscale IPv4 address and MagicDNS name when the Tailscale listener is successfully bound. If you configure a reverse proxy or another intentional hostname, list it in `HILIGHT_ALLOWED_HOSTS` (whitespace-separated). Behind a reverse proxy, the forwarded `X-Forwarded-Host` is validated against the same list, so add the public hostname there and have the proxy send it together with `X-Forwarded-Proto`. Set `HILIGHT_ALLOWED_HOSTS` to `*` to disable the check entirely, only when the server sits behind your own authentication or proxy. Mutating routes also reject a present foreign `Origin` or `Referer` (`403`); header-less CLI control requests remain allowed where supported.
- **Browser opening** - Set `HILIGHT_NO_OPEN=1`, equivalent to `--no-open`, to create or resume a session without launching a browser window.

Every command refuses a flag it does not read, with exit code 2 and the valid flags named, instead of silently ignoring a typo. `hilight <command> --help` is short; `hilight <command> --help --full` and `hilight --help --full` print every rule. `hilight --version` answers without loading the rest of the CLI.
| `hilight server` | `--verbose` | Log session and watcher events to stderr; can also be enabled with `HILIGHT_DEBUG=1`. The server writes one line per event to `~/.hilight/server.log` (or `HILIGHT_STATE_DIR/server.log`) however it was started: start and stop with the cause (including SIGTERM from a supervisor), crashes, and each session's listen, delivery, held reply, reply, and end. The file is appended, never truncated, and rotates at 2 MB into `server.log.1` and `server.log.2`. A detached server's own output (stack traces, warnings) is appended to the same file with UTC timestamps. |
| `hilight server` | `--also-listen <host>` | Also listen on this concrete address (repeatable). The CLI passes it when it replaces a running server, so the replacement keeps every address the old one served; see One server per port. |

## Telemetry

Hilight release builds send no telemetry: no Umami website ID is baked in. The telemetry code from Lavish is still there and turns on only when you set `HILIGHT_UMAMI_WEBSITE_ID` (and optionally `HILIGHT_UMAMI_HOST`). When it is on, each `hilight` run sends two requests, except `hilight --version` (also `-v` and `-V`), which sends none: a page view when the command starts, and a `command` event when it finishes. Both carry:

- the command name (for example `open`, `poll`, or `home` when you run it with no command), but not its arguments, file paths, artifact content, or prompts
- the Hilight version, `process.platform`, and `process.arch`

The `command` event also carries a `status` field: `success`, or `error` only when the CLI itself throws. A command that fails and sets a nonzero exit code is handled by the CLI framework, so it still reports `success`. No user identifier is sent. Requests time out after 1 second, and failures are ignored, so telemetry never changes what a command does.

Set `HILIGHT_TELEMETRY=0` (or `false` or `off`) to force it off.
